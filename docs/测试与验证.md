### README 旧数字的结论

原 README 写 **1121 passed / 3 skipped**，快速开始与其他页面却写过 1087、1090、586 等不同数字。此次实际采集到原始套件共 **1124 项**，与 1121 + 3 相符；关闭真实 API 后，其中 **4 项真实 LLM 测试跳过**，得到 1117 + 7。

这说明旧数字有可能来自启用真实 API 的某次运行，但仓库没有附上能证明那次结果的报告。此次没有重跑付费 API，不能追认旧结论。更准确的说法是“单元与集成测试套件”，其中包括数据库、向量检索、HTTP 接口以及部分前端源码契约检查。测试通过数量不等于代码覆盖率，也不能证明真实浏览器、安装包或所有模型厂商都正常。

### 每个 passed 都有用吗？

**不能这样保证。** 本次数字来自实际执行和 JUnit 报告，但“执行过且通过”与“能够发现错误”是两件事。38 项 Python 前端源码契约只检查文件里的约定，不执行浏览器；其余 1085 项也包含使用替身的接口测试，不能统称为端到端测试。pytest 现在会在输出末尾单列这个分类，可用 `-m static_contract` 或 `-m 'not static_contract'` 分开运行。Node 套件也混合源码契约和行为测试，不应把 192 项都叫作桌面端到端验收。

本轮对全部 40 个 Python 测试文件做了 AST 筛查，涉及 1042 个测试函数定义（参数化后为 1130 个测试项）。未发现空测试、完全没有断言或异常检查的测试、字面量恒真断言或重复测试名；这只是排查明显缺陷，无法证明断言都有效。相同函数体也不一定重复，例如不同接口各自检查未登录请求。

随后在隔离的源码副本中注入 5 种具体错误，分别执行原版与变异版。Python 结果核对了退出码、JUnit 失败数，排除了收集 / 初始化错误和跳过；Web 启动脚本核对了执行结果与断言失败。

| 故意注入的错误 | 原检查能否发现 | 加强后的检查 |
|---|---|---|
| 密码校验永远返回成功 | 能 | 能 |
| 超过上限的记忆锚点仍被接受 | 能 | 能 |
| SQL LIKE 不再转义百分号 | 能 | 能 |
| 健康接口永远返回 degraded | **不能**：原断言同时接受 ok / degraded | **能**：正常依赖必须为 ok，并新增两种依赖故障检查 |
| 注释掉 Web 启动时的刷新调用 | **不能**：注释仍含原测试搜索的字符串 | **能**：Node VM 执行真实 boot.js，断言刷新、限流和提示效果 |

5 组未变异对照均通过；加强后 5 种错误都触发了断言失败。这是有针对性的抽样，**不是全项目变异覆盖率，更不是每一项测试都有价值的证明**。VM 验证浏览器 API 的调用效果，不验证真实浏览器的布局、缓存或安装包。

此外，移除了重复的前端文件存在检查，以 HTTP 资源测试覆盖该约定；补强了表注册集合、空列表遍历、状态类别等断言，避免漏表或空结果也被视为成功。本机审计明细和变异前后日志保留在 `.pytest-data/test-function-audit.json`、`.pytest-data/mutation-before/reports/` 与 `.pytest-data/mutation-after/reports/`。

### 7 项跳过

| 数量 | 原因 | 启用条件 |
|---|---|---|
| 1 | MySQL 连接池断言不适用于 SQLite | 使用下述专用 MySQL 测试库 |
| 4 | 真实 LLM 的连通性、对话、流式、错误 Key 测试默认关闭 | 显式传 `--live` 并提供 API 配置 |
| 2 | 没有用户自备的真实酒馆预设文件 | `HNE_REAL_PRESET` 指向相应 JSON 文件 |

本轮仍有 3 条第三方弃用警告：Starlette 对 httpx / AnyIO 接口的提醒，以及 Chroma 的旧集合配置提醒。未隐藏警告，也未为消除警告升级运行时依赖。

## 常用命令

在仓库根目录执行：

```powershell
./.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
./.venv/Scripts/python.exe -m pytest -q --junitxml=.pytest-data/results.xml
./.venv/Scripts/python.exe -m ruff check app scripts tests desktop/backend_entry.py desktop/scripts
./.venv/Scripts/python.exe scripts/check_docs.py
./.venv/Scripts/python.exe scripts/init_db.py --check-sql
./.venv/Scripts/python.exe scripts/verify_zero_config.py
cd desktop
npm test
```

后端测试强制将 SQLite、向量库、日志和测试密钥隔离在 `.pytest-data/`。默认不读取开发者 `.env`，也不继承真实数据路径或 API Key。测试账户仍使用真实 bcrypt，仅将测试 cost 调低为 4 以减少等待；应用默认值仍为 12。需要验证较高 cost 时可设置 `HNE_TEST_BCRYPT_ROUNDS=12`。

ONNX 集成测试会执行真实推理；首次运行需要联网下载约 80 MB 模型。Windows 测试还使用日志队列、本地端口和子进程，受限沙箱可能报 `WinError 5` 或 `spawn EPERM`。应在允许这些操作的本机环境重跑，不能把这类失败统计为通过。不要在同一 checkout 中并行运行多个后端测试进程。

### 真实 API（显式启用）

在 `.env` 或进程环境中设置 `HNE_DEFAULT_LLM_BASE_URL`、`HNE_DEFAULT_LLM_API_KEY`、`HNE_DEFAULT_LLM_MODEL`，然后运行：

```powershell
./.venv/Scripts/python.exe -m pytest --live -m live -q
```

这会请求所配置的服务商，可能产生费用。仅提供配置但不传 `--live` 时仍跳过。

### MySQL（专用测试库）

先创建专用库和仅有该库权限的账号。测试库名必须以 `_test` 结尾，避免误用日常数据库：

```powershell
$env:HNE_DB_BACKEND='mysql'
$env:HNE_TEST_MYSQL_HOST='127.0.0.1'
$env:HNE_TEST_MYSQL_PORT='3306'
$env:HNE_TEST_MYSQL_DB='yunmeng_test'
$env:HNE_TEST_MYSQL_USER='yunmeng_test'
$env:HNE_TEST_MYSQL_PASSWORD='<测试库密码>'
./.venv/Scripts/python.exe -m pytest -q
Remove-Item Env:HNE_DB_BACKEND
```

不会复用 `.env` 或 `HNE_MYSQL_*` 中的应用账号。MySQL 路径本轮未实测；SQLite 结果不能替代 MySQL 验证。
