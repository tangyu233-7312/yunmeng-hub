## 7. 已知坑（新对话最容易踩的）

- **`#view` 是常驻元素**：视图内的按钮监听器**每次渲染后都要重绑**（`mount()` 会换掉节点）；
  只有挂在 `#view` 上的事件委托才能"每批只绑一次"。混起来 = "点一次按钮弹出 N 个窗" 或
  "切一次筛选后按钮全失效"（这两个 bug 都真实发生过）。
- **提示词只能有一个装配入口**：`engine.build_session_prompt` —— 对话与「查看提示词」预览共用它。
  插件、状态、预设都必须在这里接上，否则"预览与实际不一致"（踩过两次）。
- **整页加载不许卡死**：先判断"我还是当前批次吗"再动 DOM；列表接口带 20s 超时；
  失败一律画 `ui.js::mountError`（报错 + 重试按钮）。
- **状态协议要放在提示词最末尾**（`render_contract`）：夹在中间会被后面的守卫盖过去（真实模型实测漏掉过）。
- **探针里别把界面停在"下一节要点导航过去"的那个页面上**：点导航会触发**异步**重渲染，
  紧接着的一次 `[data-*]` 点击（或派发合成事件）可能落在**旧** view signal / 旧节点上；
  重渲染 abort 它之后，那些 `if (signal?.aborted) return;` 的分支就会"事情做了一半、界面毫无反应"
  （骰子节真的踩到：纯聊天会话建好了却没被打开；拖动条那两条也偶发因此变红）。
  收尾时切到别的页面；要派发事件前先确认那个元素属于**当前这次渲染**。
- **加了新接口/新列之后：先重启 uvicorn 再跑 smoke**（第十五轮又踩了一次：
  冒烟测试整段 404，因为跑的还是旧进程）。列则要跑 `scripts\migrate_db.py`。
- **前端模块必须在 `index.html` 的 importmap 里登记**（`tests/test_console.py` 两条断言守着）。
- **语义字段要在前后端各写一遍注释**：第十五轮的 `display`（"给人看哪一份"）两边读法差点相反
  —— 接口数据对、单测全绿，但界面显示错了文本，最后是**看截图**才发现的。
- **PNG 导入不会把图片入库**：`import_card_from_png` 抽完卡数据就把图片字节丢了
  （`character_card_service.py:872-914`、`png_card.py:188`）。想让那张图当 VN 立绘 / 背景 / 头像，
  只能在卡编辑器里填地址（`http(s)://` 或 `data:image/...;base64,`，单条 ≤300,000 字符、最多 24 张）。
  第十六轮修的就是这里的**界面文案与实现不符**（弹窗曾写"图片本身还能当人物立绘…会自动识别"）。
  真要"导入即自动当立绘"得先定存储方案：上传上限 10MB vs 单条地址 300,000 字符、base64 膨胀 4/3，
  只有"导入时压缩内嵌"或"加静态文件挂载"（目前只挂了 `web/`）两条路。
- **翻译只有一个语言设置，源语言自动识别**（第十六轮定稿）：用户只选「翻译成什么语言」
  （默认 `简体中文`），两个方向共用它 —— 想"把我写的中文译成英文再发"就把目标选成英文，
  不再有第二个"输入侧语言"（用户真的把两个并排的语言框读成了"英文→中文"，而语义恰好相反）。
  **没有外语卡也能测真模型翻译**；★ 中文用户写中文、目标也是中文时会命中"已经是目标语言"
  → 0 token、什么都不发生 —— 这是设计不是 bug。
- **别把假名/谚文算进"中文"**（第十六轮踩到的真 bug）：旧判据是"CJK 占比 ≥40%"，而
  `_CJK_RE` 把平假名/片假名/谚文一起算了进去 → **日文、韩文回复被判成"已经是简体中文"，
  0 token 静默不译**（"日文自动识别后翻成中文"看着配好了、实际什么都没发生）。
  现在：出现假名/谚文 ⇒ 不是中文；中文还要再分简繁（含繁体专用字要转简，含简体专用字要转繁）；
  目标日文/韩文也各自用假名/谚文判定。判据全部是"省钱的短路"，判不出来就老实译。
- **卡的「自定义系统提示词」是整体替换，不是追加**（`prompt_builder.py:261-289`）：填了它，
  引擎按人设字段**自动拼装**的那一份就没了，内置的"你正在扮演角色 X…"也一起没了。
  真实踩过：测试卡里只写一句 "always reply in English"，模型于是**跟着用户的语言走**
  （用户用中文问就回中文、偶尔回英文 = "一会中文一会英文"），**没有任何报错**。
- **★ 想用卡去"压"模型的输出语言，只能靠 system 角色 —— 尾注压不住**（第十六轮两次真机打回）：
  ① 尾注（`post_history_instructions`）确实是**最后一条消息**、裁剪层还专门保住它
  （`context_manager.py:299-304`）、适配器 1:1 全发 —— 但 deepseek-flash **照样回中文**；
  ② 原因：卡 `system_prompt` 留空时，system 角色里是引擎用**中文**拼装的
  「你正在扮演角色…」，中文框架 + 中文提问 + 中文历史把尾注压过去了。
  **正确做法：把语言规则写进卡的 `system_prompt`，并写成英文的完整提示词（人设也得自带）**。
  ③ 残余中文因素：项目的「当前状态」块与状态输出契约（`render_contract`）是中文的、
  追加在系统提示词最末尾 —— 对照卡 `data/test-cards/translate-test-emily-pure-en.json`
  （不带状态栏）就是用来二分定位这一条的。
  ★ 另一条边界：**绑了预设的会话由预设决定系统提示词与尾注位置**（`prompt_builder.py:721-725`）。
- **VN / 翻译的探针证明不了"观感与质量"**：探针用内嵌纯色小图 + 假模型，只能证明**逻辑与链路**。
  真立绘排版、真模型的译文质量与 token 花费**必须人工跑一轮**（方法与证据边界见
  `docs/paper-materials.md` §5.7 / §5.8 的两段"证据边界"）。

## 11. 第七轮：混合检索融合 + 可复现 benchmark（2026-09-26）

### 11.1 改之前：两条互不相干的通道

关键词通道（世界书）**只按 insertion_order 排序、没有相关性分**，自己吃 `token_budget`；
语义通道（记忆）按余弦相似度取 top-k，自己吃 1200 字上限。两路从不互相知道对方存在 →
同一段内容可能进提示词两遍、短而精准的设定被长而含糊的回忆挤掉。

### 11.2 现在：`app/narrative/retrieval.py`（唯一入口）

```
① 召回  关键词（命中数 + 0.1×命中字数）+ 语义（余弦相似度）
② 融合  RRF：Σ w_c/(60 + rank_c)（默认；weighted 只用于消融）
③ 去重  跨通道按归一化文本去重，两路名次合并到胜者（RRF 吃两票）
④ 重排  默认 tiebreak：融合分说了算，**完全同分**时才按"每路归一化证据强度"裁决（1e-6 量级）
⑤ 装填  **两路共享一个 token 预算**（= 世界书 token_budget，缺省 1024），贪心装填、
         至少保留最高分那条；被挤掉会在 warnings 里说明原因
```

- 唯一入口 `engine.build_session_prompt`；预设预览也走它（显式不接语义通道并如实标注）。
- 可解释：`retrieval_summary`（一行计数）+ `retrieval_items`（逐条来源/名次/分数/去留原因），
  在「查看提示词」里显示；探针 10.11 有断言守着。
- 降级：两路各自 try/except，失败原因**必须**报出来（静默降级是 bug）。

### 11.3 benchmark：`scripts/benchmark.py`

```
.\.venv\Scripts\python.exe scripts\benchmark.py
  → 控制台表 + data/benchmark_report.json + data/benchmark_report.md
```

数据集 `scripts/benchmark_data/`：`retrieval_cases.json`（合成：12 query / 10 条目 / 11 记忆）、
`state_cases.json`（10 条状态校验用例，**带期望下场**，顺带是校验语义的回归测试）。
**不调用任何大模型**；语义通道默认取标注相似度，`--semantic embedding` 可换本地 onnx 模型。

实测（2026-09-26）：

| 策略 | Recall@1 | Recall@3 | MRR | nDCG@5 | 注入条数(均) | 注入token(均) |
|---|---|---|---|---|---|---|
| `keyword_only` | 0.4861 | 0.5278 | 0.7917 | 0.5768 | 1.17 | 34.7 |
| `semantic_only` | 0.2917 | 0.3889 | 0.7083 | 0.4493 | 2.00 | 42.7 |
| `rrf(+tiebreak)` ★默认 | **0.5139** | **0.9167** | **0.9167** | **0.8962** | 3.08 | 74.5 |
| `weighted(+tiebreak)` | 0.5139 | 0.9167 | 0.9167 | 0.8962 | 3.08 | 74.5 |
| `rrf(+blend 词面重排)`（负面对照） | 0.3056 | 0.8750 | 0.8194 | 0.7765 | 3.08 | 74.5 |

两条被数据推翻的直觉（都写进了代码注释与测试）：

1. **用字面重叠重排有害**：Recall@1 0.51 → 0.31（语义通道的价值正是"没有字面重叠的同义改写"）。
2. **RRF 同分很常见，"怎么裁决同分"和融合策略一样重要**：key 序 0.5139 / 先验分 0.2639 /
   只按语义分 0.3333 / 每路归一化证据 0.5139 → 默认选最后一种。

## 15. 第十一轮：总结按钮的反馈 + 防重复总结（2026-09-26）

### 15.1 用户报的真实事故

> "横幅给的总结按钮点下去后没有给用户反馈是否正在总结，刚刚我就犯下一个错误。
> 不知道有没有开始总结，点了开几遍，结果 ai 也给我总结了好几遍。"

**两条根因**：① 横幅按钮点了没反馈（面板里那个有 loading，横幅那个漏了）；
② 后端没给同一会话的总结**串行化** —— 并发请求各自都看到"有未总结的轮次"，于是各跑一次模型。

### 15.2 修法

- **界面**：点击后**在第一个 await 之前**就把按钮换成 `⏳ 总结中…` 并 `disabled`，
  横幅上再补一句"正在总结（要调用一次模型，请稍等）…"；结束/失败后恢复并给结果，
  失败时明说"这次没有重复总结（上一次还在进行中，或已经没有新内容可总结）"。
  （同步可见的反馈才叫反馈 —— 用户点完立刻能看到变化，就不会再连点。）
- **后端**：`summary.py` 每个会话一把锁，`merge_block` **非阻塞抢锁**；抢不到直接返回
  `BUSY_REASON`，**绝不跑模型**；`POST /memory-summary/run` 返回 **409**；面板 `GET` 带 `busy`。
- **顺手修**：没有任何完整轮次时拒绝总结（之前会把**开场白**当成"第 1 轮"总结掉、白花一次调用）。

### 15.3 「照抄旧记忆生成新记忆」

用户给的参考产品说明是：**"照抄旧总结并压缩最新的聊天记录生成新的记忆"** ——
这正是我们模式 4 的语义（旧总结照抄 + 最新一段聊天本地压缩后追加），
区别只是我们用**本地逐条摘录**代替"压缩"这一步，所以它是唯一的 **0 token** 模式。
面板文案已对齐该措辞。★ 五个模式的原始提示词拿不到（官网营销页 / 网页版登录壳），

## 16. 第十二轮：状态漂移曲线 + 状态遥测（2026-09-26）

反事实这条回注**模型自己写下的**状态（于是漂移一轮轮累积）。

## 17. 第十三轮：骰子插件 + 五套总结提示词 + 删掉群聊（2026-09-26）

### 17.1 骰子插件（`app/narrative/dice.py` + 插件类型 `dice`）

**为什么要它**：大模型没有真随机（需要成功就写 18、需要失败就写 3），
而跑团/检定/掉落表的乐趣建立在"结果不由叙述者决定"上。用户笔记里也一直有
"插件化架构 + 骰子"这一项。

两条路都通，且都落在**同一个求值器**上：

```
玩家：/r 1d20+5 力量检定        → 后端掷 → 🎲 力量检定 1d20+5 = 17（骰子 12）
模型：他抬手格挡。<roll>1d20+5</roll> → 系统把标签替换成明文点数（下一轮模型看到的就是它）
```

- **受控求值**：自己写的递归下降解析器（分词 → 四则 + 一次比较），
  **不用 eval、不放开 JS**（与"插件不执行第三方 JS"同一条红线）。
  支持 `NdM` / `kh`·`kl` 取高取低 / `!` 爆炸骰（有深度上限）/ 括号 / `<= >= < > = !=` 成功判定 / `# 说明`。
  上限：表达式 ≤240 字符、≤100 颗骰、≤1000 面、括号 ≤8 层、中间结果有上限；
  超限**拒绝并说明原因**（不"截断后照算"）。
- **点数落库、绝不重掷**：`/r` 在 **`engine.save_user_message`（用户消息唯一落库点）** 掷定，
  写进 `messages.rolls_json`（含逐颗骰面与取舍过程）。所以刷新页面、「查看提示词」预览、
  重新生成读到的都是**同一组数字** —— 若改成"构建提示词时现掷"，
  点一次预览就会掷出另一个数（本项目对"预览与实际不一致"零容忍）。
- **`<roll>` 一律剥掉**：`engine.save_assistant_reply` 里结算并替换成
  `（掷骰 1d20+5 = 17）`，**插件没启用时也剥**（绝不让用户看到原始协议文本）。
- 提示词两处：**规则块**（"你没有随机数能力 + 怎么写 `<roll>`"）由
  `plugin_runtime` 追加在系统提示词末尾；**本轮点数**是客观事实，
  由 `build_prompt(dice_block=…)` 放在「当前状态」之后（数据不占末尾那个"必须照做"的位置）。
- 前端：消息底下渲染 🎲 骰子气泡（成功/失败染色、悬停看明细）；插件编辑器有骰子专属表单。
- 插件配置：触发词 / 默认表达式 / 上限 / `allow_model_roll` / `show_detail` / `explain`，
  内置目录一键添加（`trpg_dice`），停用即失效。

## 18. 第十四轮：角色卡 VN 模式（立绘 / 表情）（2026-09-26）

### 18.1 一句话设计

**表情不是新协议，它就是状态栏里的一个字段**（默认 `mood`）。
卡里声明「表情名 → 立绘地址」，模型照常每轮输出 `<state>`，
后端按当前状态算出"现在该显示哪张立绘"，前端只负责画。

```
卡 extensions.hne.vn:
  { "background": "…/classroom.png",
    "sprites": {"平静": "…/calm.png", "生气": "…/angry.png"},
    "expression_field": "mood", "default": "平静", "position": "center" }

模型这一轮: <state>{"mood": "生气"}</state>   → 会话页立绘换成生气那张（名牌上显示「生气」）
```

为什么挂在状态栏上（而不是新加一个 `<expr>` 标签）：
1. 模型已经每轮输出状态块了，多一个字段**不需要任何新协议、不多一次调用**；
2. 立绘与文字剧情天然同步，不会"嘴上说生气、脸上还在笑"；
3. 与第六轮"状态栏字段由卡/世界书说话"一致 —— 作者声明了哪些表情，
   建会话时会把它们写进**该字段的可选值描述**，模型于是知道该填哪些词。

### 18.2 位置与文件

| 关注点 | 落点 |
|---|---|
| 校验 / 选图 / 舞台数据 | `app/narrative/vn.py`（纯函数：`normalize` / `sprite_url` / `stage` / `ensure_expression_field`） |
| 存进卡时就洗干净 | `character_card_service._sanitize_extensions`（create / update / import 三条写入口） |
| 建会话时补表现字段 | `sessions.create_session` → `vn.ensure_expression_field` |
| 接口吐舞台数据 | `SessionDetail.vn`（`serialize_detail`，由**后端**算好当前立绘） |
| 界面 | `web/js/views/chat.js`（🎭 开关 + 舞台四层）/ `cards.js`（卡编辑里的 VN 段）/ `styles.css` |

### 18.3 安全与取舍

- 图片地址只收 `http(s)://` 与 `data:image/(png|jpeg|webp|gif);base64,`。
  `javascript:` / `file:` / **`data:image/svg+xml`** 一律拒绝（SVG 可能带脚本；
  虽然 `<img>` 里多数浏览器不执行，但"能不能执行"不该取决于浏览器版本）。
- 单条地址 ≤ 300KB 字符、最多 24 张立绘；**坏图不废卡**（丢那一条 + 记 warning）。
- 背景用 `<img>` 而不是 CSS `background-image`：地址来自用户，拼进 `style` 属性
  就要担心 CSS 字符串逃逸；`<img src>` 过一遍 `esc()` 就够。
- 开关状态存**浏览器本地**（按会话）：它是"看的方式"，不是数据，不该为它发一次 PATCH。
- 纯聊天 / 没声明 VN 的卡 → `detail.vn = null`，界面里连开关都不显示。

### 18.4 顺手修的探针竞态（同类问题第二次出现）

`11.拖动大小` 那两条**偶发**变红（拖了宽度一点没变）。根因与第 17 轮那条同源：

```
点一下「叙事会话」导航（此刻已经在该页）→ 仍可能触发一次异步重渲染
→ 探针紧接着 querySelector('#chat-resize') 拿到**旧节点**并派发合成指针事件
→ 旧节点的监听器已随旧 view signal 一起 abort → "拖不动 / 双击没反应"
```

修法：拖动前**先切到别的页再切回来**（探针里已有这个手法），保证这一次视图是新渲染的。
> 教训：探针里凡是要"派发事件给某个元素"，都要先确认那个元素属于**当前这次渲染**。

## 19. 第十五轮：自动翻译中间件（跨语言对话）（2026-09-26）

### 19.1 一句话设计

**一条消息最多两份文本，界面按 `display` 显示该看的那一份，一键切换。**

| | `content`（永远是**模型看到的文本**） | `translation.text`（另一份） | `display` |
|---|---|---|---|
| 输出侧（reply） | 模型说的原文（外语） | 译文 | `translation`（默认看译文） |
| 输入侧（input） | **译文**（模型看到的就是它） | 用户的原文 | `content`（默认看原文） |

把译文写进输入侧的 `content` 是个刻意的取舍：**提示词装配不需要任何"替换历史"的机制**
（它本来就只读 `content`），少一处改动就少一处"预览与实际不一致"的机会。

### 19.2 三档模式（成本必须由用户选，默认关闭）

| 模式 | 额外调用 | 说明 |
|---|---|---|
| `off` | 0 | 默认 |
| `prompt` | **0** | 只在系统提示词**最末尾**加一句「正文一律用 X 书写」。不保证（模型可能不听话），但不花钱 |
| `middleware` | 每轮 1 次 | 生成之后真的调一次模型翻译；原文/译文都留着，可切换 |

方向：`reply` / `input` / `both`。还能在面板里**指定另一个模型**专门翻译
（与"总结用哪个模型"同一套：配置被删/停用就退回会话模型）。

> ★ **第十六轮改过这里**：语言设置从"输出侧 + 输入侧各一个"简化成**只有一个目标语言**
> （默认 `简体中文`），源语言自动识别（英文 / 日文 / 韩文 / 繁简都能认）。
> 详见 §29（handoff.md）与本节末尾的"第十六轮补充"。

**两条省钱的判断**（本地做，不调模型）：
- **已经是目标语言就不译** → `used_model=false`、**0 token**；
- **太长就不译**（>6000 字，一轮几千字的翻译很贵，而且多半是整段复述），如实说明。

> ★ 第十六轮修正：旧版"已经是目标语言"的中文判据是 **CJK 占比 ≥40%**，而 CJK 集合里
> 混进了**假名与谚文** → 日文、韩文回复被判成"已经是简体中文"而**静默不译**。
> 现在：出现假名/谚文 ⇒ 不是中文；中文再分简繁；英文仍是 ASCII 字母占比 ≥70%。

### 19.3 落库与成本

- `narrative_sessions.translate_settings_json`（会话级设置，与记忆面板同构）
- `messages.translation_json`（结果 + 方向 + 语言 + 模型 + token + error）
- 翻译花的 token **计进 `session.total_tokens`**，并在这一轮的 `notes` 里说一句
  （"本轮回复已由翻译中间件译成简体中文（47 token）"）—— 花在翻译上的钱必须看得见。
- 失败**只记 notes / 日志**：回复一个字都不会丢（与剧情总结降级同一套哲学）。

### 19.4 一个容易被忽略的细节：记忆库写"给人看的那一份"

跨语言会话里，用户用中文提问、检索也是中文，而 `content` 在输入侧是译文、输出侧是原文。
所以写长期记忆时用 `_display_message()` 取**用户读到的语言**那份 ——
否则下一轮用中文提问，召回质量会明显下降（这是"翻译让记忆变哑"的隐蔽 bug）。

### 19.5 界面

- 头部「🌐 翻译 / 🌐 翻译开」按钮 → 面板：总开关、模式、方向、**一个**语言
  （「翻译成什么语言」，默认简体中文；源语言自动识别）、翻译用哪个模型、
  保留原文、以及"已译 N 条 / 翻译累计 N token / 这一轮预估 N token"。
- 消息下方一颗 🌐 说明（"简体中文译文 · 47 token"），外加「看看另一份」——
  **两份文本都在 DOM 里**，切换是纯前端的：不发请求、不改数据、刷新后按 `display` 复原。
- 留档截图：`data/ui_probe_translate.png` → `docs/translate-screenshot.png`。

## 20. 第十六轮（四续）：跨页串台与"那块白"的定案（2026-10-02）

> 详细推导见 `docs/handoff.md` §29.15。这一节只留"下次还会踩"的部分。

### 20.1 坑①：`AbortController` 接力漏了一环 = 监听器永不失效

```js
// ✗ 改之前：换了新控制器，但它不在路由信号的链上
function nextController(current) { current?.abort(); return new AbortController(); }
```

`#view` 是**常驻**的，切页只换内部内容。视图把委托监听器挂在 `#view` 上时，
能不能在切页后失效，**完全取决于这个 signal 有没有接在路由信号上**。
"每次都换一个新控制器"看着很安全，实际上把父子链**剪断了** —— 那个控制器
没有任何人会 abort 它。

**症状**：插件页点「删除」弹两个窗；第二个是"删除这套预设？"，
并且拿**插件的 id** 去打 `/prompt-presets/{id}` → 404「提示词预设不存在」。
原因是预设页与插件页的卡片都是 `.cc`、删除按钮都叫 `data-act="del"`。

**教训**：`history` 里凡是"新建控制器/新批次"的写法，都要问一句
**"谁会 abort 它？"**。只有 abort 上一批是不够的，必须接力到路由信号。

### 20.2 坑②：静态测试只数 `{ signal }` 的个数 —— 挡不住这类 bug

`test_view_delegated_listeners_are_abortable` 数的是
"`root.addEventListener(` 的个数 ≤ `{ signal }` 的个数"。
而 presets.js 是通过 `withSignal(root, 'click', …)` 间接绑的，
signal 变量名也换了 —— **数字对得上，bug 照样存在**。

**改法**：加了三条**认结构**（而不是认字数）的静态测试，见 §29.15 ⑥。
另外在五个视图里都加了与 signal 无关的 **`data-view` 归属校验** ——
"在 A 页点按钮、B 页的动作被执行"从此在结构上不可能发生。

### 20.3 坑③：深色主题断言自己会漏也会误报（**修了三次才对**）

* 只比 `backgroundColor` 的亮度 → **漏掉透明背景的块**（白来自父级或子文档）。
* **渐变漏检**：渐变画在 `background-image` 上，`backgroundColor` 读出来是**透明**的
  —— 角色卡页每张卡的开场白预览框 `.cc-greeting`
  （`linear-gradient(180deg,#f7f9fc,#f2f5fa)`）两次都被当成"透明块"跳过；
  而且它当时**根本不在采样清单里**。
  **"没测到"和"通过"长得一模一样，这是最危险的一类假绿。**
  现在采样器解析渐变的所有色标、取最亮那个参与判断，`.cc-greeting` 进必采清单
  （缺了直接判失败）。用桩在 Node 里验过：喂旧写法得到 `.cc-greeting=grad249` → 判亮、失败。
* 按"亮度 > 140 就算浅色"放行 → **品牌蓝被误判**（`rgb(124,156,255)` 亮度 158）。

**现在的采样规则**：解析渐变的所有色标（取最亮）→ 透明/缺失的元素单独列进 `跳过`
字段（不再假装测过）→ 品牌色按颜色值放行；采样点包含**角色卡页 + 已打开的详情弹窗**。

### 20.4 坑④：iframe 不继承父页面的 CSS 变量

HTML 开场白渲染在 `srcdoc` iframe 里，那是一份**独立文档**：
父页面的 `--surface` 之类**一个都进不去**。
所以"把写死的 `#fff` 收进变量"这个修法对它无效 —— 必须**渲染时把当前值注入 srcdoc**
（`ui.js::richDocHead()`）。**凡是 iframe / 子文档 / canvas 里的颜色，
主题变量化都管不到，要单独处理。**

### 20.5 我犯的错：把"我找到的 bug"当成"用户说的那个 bug"

用户说"角色卡页有一块白"，我查到 iframe 里确实写死 `#fff`，就宣布**定案**；
复测后用户说"还是在" —— 他看到的其实是**渐变预览框**（`.cc-greeting`）。
**正确顺序：先让用户确认位置（圈一下/截图），再宣布定案。**
"我找到了一个真 bug" ≠ "我找到了你说的那个 bug"。

### 21.2d 采样器第四次修正：点状高光 ≠ 浅色块

星点一加，采样器立刻把 `body` 判成"浅色块 207"（它把 14 层星点里最亮那颗白点当成了一整块 80% 白）。
修法：**按层切分 + 按声明尺寸分流** ——

* 用**括号配对**切出每一层渐变（不能按逗号 split，`rgba(...)` 里也有逗号）；
* 声明尺寸 ≤ 4px 的径向渐变 = **点状高光**：不参与"亮块"判定，但**单独报告**，
  并有自己的断言（合成峰值 40~210）；
* 其余层照旧参与"亮块"判定。

> 四次修正：透明 → 渐变 → 半透明 → 点状高光。**"看起来亮不亮"是语义问题，不是一个字段能回答的**；
> 每加一种画法，断言就要长一格，而且**必须打印"跳过了什么、为什么"**。

### 21.4 内置插件升级：从"删掉重加"到"一键更新"

结构性问题：内置插件（尤其主题）会升级，而**插件内容在"添加"那一刻就被拷进数据库**了。
前三轮每次改完主题，用户都得删掉重加，而且**没有任何地方告诉他这件事**。

| 位置 | 改动 |
|---|---|
| `catalog_for` | 目录条目新增 `update_available`（已添加且内容与当前目录不同；同名但类型不同 = 用户自己的，不算） |
| `add_from_catalog` | 没添加 → 201 新建；添加过但旧 → **200 覆盖成最新**；已最新 → 400「已经是最新版」；返回 `(row, updated)` |
| `api/v1/plugins.py` | `POST /plugins/catalog/{key}` 按情况回 201/200 |
| `plugins.js` | 有更新时显示 `有更新` 徽章 + 「**更新到最新**」按钮；已最新则是禁用的「已添加」 |

### 22.2b ★ 阶段 2 抓到的三个真 bug（都靠"让它失败"的用例逼出来）

1. **自检假通过**：第一版自检只看 HTTP 200，而后端当时 MySQL 与向量库**都是坏的**
   —— 本项目的 `/health` 在组件降级时**照样返回 200**。已改成逐项检查 `components.*.status`。
2. **`tqdm` 没打进包**：ChromaDB 下载模型要用它，缺了直接 `ValueError`，
   报错信息完全看不出跟 tqdm 有关。
3. **`HNE_DESKTOP_BACKEND` 被无声忽略**（两层）：① `main.js` 忘了把它传进候选列表，
   用户指定的路径**从没被检查过**；② 修完第一层才发现，指定路径不存在时会
   **悄悄落到默认候选**。正解：**显式指定 = 只认它**，不存在就失败。
   > 单测没抓到的原因：单测**自己**把 explicit 放进了 candidates —— 而那正是 main.js 忘做的事。

### 22.3 发布闸门收紧：`--name` 从 WARN 改成 BLOCKER

```powershell
.\.venv\Scripts\python.exe scripts\prepublish_check.py --name <你的真名>
```

* **真实事故**：`docs/next-electron-and-github.md` 里写着贡献者的**真账号名**，
  而当时只报 WARN ⇒ "闸门通过"却带着真名准备发布。已改成 **BLOCKER**（命中就退出码 1）。
* BLOCKER 的**措辞里不复述那个真名**（否则"为了排掉痕迹"的过程又把它写了一遍）。
* ★ 另一个坑：`--root <干净副本>` 是**遍历文件系统**的，而 `robocopy` **不认 `.gitignore`**，
  会把被忽略的运行期数据一起复制过去 ⇒ 报出一堆假 BLOCKER。
  要知道"git 真正会提交什么"，用：
  ```powershell
  git ls-files -co --exclude-standard
  ```
* 本轮实测：按 git 规则复制出的 **193 个文件**（含 `desktop/`）→ **0 BLOCKER**。

### 22.3b ★ `.gitignore` 上返工三次的坑（值得记住）

目标是"让 `desktop/build/icon.ico` 进版本库（随包发布），而 290MB 构建产物不进"：

1. 裸写 `build/` **会匹配任意层级**（gitignore 规则：不含斜杠的模式匹配任意层级），
   于是 `desktop/build/icon.ico` 被**静默忽略**，而 README 却写着"图标随包发布"。
2. 修成 `!desktop/build/**` —— 豁免**太宽**，PyInstaller 工作目录（234MB）
   与暂存模型（87MB）全都准备进库。
3. 修成 `desktop/build/*` + `!desktop/build/icon.ico` 也不行 ——
   **父目录被忽略时，里面的文件无法用否定模式放行**。
4. 最终解法：把 Python 那两条锚定到**仓库根**（`/build/`、`/dist/`，它们本来就只指根目录），
   再精确排除 `desktop/build/` 下的生成物子目录。**共 193 个文件、无大文件**。

> 构建脚本结束时会用 `git check-ignore` 复查这两件事并打印结论 ——
> 因为这类规则一旦被"顺手简化"，失效方式是**静默**的。

### 22.4 本机开发环境三个坑（写进 `desktop/README.md` 了）

1. **`ELECTRON_RUN_AS_NODE=1` 写在宿主环境里** → `electron.exe` 退化成纯 Node，
   `require('electron')` 返回**路径字符串**，主进程什么都不做就退出（**退出码 0、无报错**）。
2. **npm 11 默认不执行安装脚本** → Electron 二进制没下载，`node_modules/electron/dist/` 是空的。
   修法：`npm rebuild electron --foreground-scripts` 或 `node node_modules/electron/install.js`。
3. **`extract-zip` 解压到一半被系统中断** → 只落地 `locales/`，**退出码还是 0**。
   改用 PowerShell `Expand-Archive` 即可（缓存里的 zip 是完整的）。

> 这三条**只影响本机开发环境**，与"该提交什么"无关（`node_modules/` 本来就被忽略）。

### 23.2 装出来的那份里有什么

| 位置 | 内容 |
|---|---|
| `resources/app.asar` | **只有** `src/**` 与 `package.json`（13 个文件）—— 用白名单，`desktop/test/` 不会被带进去 |
| `resources/backend/` | sidecar 整份（863 个文件 / 293.8 MB），`extraResources` |
| userData（**安装目录之外**） | 配置 `config\.env`、日志、向量库 —— 卸载重装不丢，卸载也**不删** |

### 23.3 阶段 3 的三个真问题（都不是"多虑"）

1. **打包态会读安装目录里的 `.env`**（安全洞，最值得记）。
   `appRoot = __dirname/../..` 打包后就是安装目录，"仓库根兜底"于是变成读
   `resources/.env`：轻则往只读目录写配置报 EPERM，重则**拿别人的数据库口令与签名密钥去连库**。
   ⇒ **"绝不把 `.env` 打进安装包"只做了一半**，另一半是"打包态绝不去读它"。
   新增 `src/packaging.js`（纯函数、有单测），验收脚本也钉了一条。
2. **electron-builder 会重下一份 Electron**（136MB）。本机实测该下载约 0.1 MB/s，
   4 分钟只走 3.67MB。⇒ `build.electronDist` 指向 `node_modules/electron/dist`（已有那份）。
3. **NSIS 工具链的下载/解压会静默卡死**（无网络活动、无输出、CPU 不动；
   缓存里只剩空目录 + `.lock`），而同一 URL 用 PowerShell 直下十几秒、SHA256 一致。
   ⇒ 构建脚本**自己下、校验、用 7z 解压**，并按 electron-builder 的命名规则
   （`<文件名>-<URL 的 djb2 base36 前 5 位>`）与它认的 `.state` 预置缓存，于是它直接命中。
   顺带"离线可重复"：缓存备好之后打包不再需要网络。

### 23.4 ★ 我在这一轮"自己骗自己"的四处（比 bug 更浪费时间）

| 脚本报的"失败" | 真相 |
|---|---|
| 没有确认打包形态 / 没有进设置页 | **PowerShell 5.1 的 `Get-Content` 默认按 ANSI 解**，UTF-8 中文日志全乱码 ⇒ 现在一律 `-Encoding UTF8`，并让应用多打一行**纯 ASCII** 的 `[state] ...` |
| app.asar 里有多余内容（`\src`） | `asar list` 也列**目录项**，我只按"文件"正则过滤 ⇒ 只看文件项 |
| 后端日志里没有 `[self-check] OK` | 自检子进程的输出由**壳**接管，写在**桌面日志** ⇒ 判据改成桌面日志的"退出码=0 且后端结论=ok" |
| smoke 2 项红（向量库） | 后端向量库指到 temp，而 smoke 直连仓库 `data/chroma` —— **环境不一致** ⇒ 两边设同一个 `HNE_CHROMA_PERSIST_DIR` 后 184/0 |

另：`-AsByteStream` 是 PowerShell 7 的（5.1 没）；PowerShell 脚本**必须带 UTF-8 BOM**
（否则 5.1 按 ANSI 读、中文全乱）；**函数参数不能叫 `$Input`**（自动变量，会让函数
算出与输入无关的常数且不报错）。
