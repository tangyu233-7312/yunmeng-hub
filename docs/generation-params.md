# 模型配置参数设计（前端对接说明）

> 本文档定义「API 配置」表单里每个参数的含义、取值范围与界面文案。
> 后端实现见 `app/llm/params.py`，数据库表见 `llm_providers`。

---

## 一、最重要的一条规则

### `max_tokens`（最大输出 Token）**包含思考过程**

这不是一句可有可无的说明，而是**必须显示在界面上的硬约束**。

```
    max_tokens（最大输出）
        ├── 思考过程 token（reasoning_tokens）   ← 推理模型专用
        └── 正文 token（content）
```

**实测数据**（`deepseek-flash`，一次叙事场景描述）：

```
completion_tokens = 433
    ├── reasoning_tokens = 380   ← 思考，占 88%
    └── 正文             =  53   ← 用户真正看到的字
```

**后果**：用户把「最大输出」设为 500，模型是推理模型，
思考吃掉 450，正文只剩 50 —— 用户会认为「AI 被截断了」，但其实是配少了。

这条规则与 SillyTavern（酒馆）的默认行为一致，属于该领域的通行约定。

### 界面上的推荐文案

```
最大输出 Token                    [ 2048 ] ⓘ
└─ 包含思考过程的 Token。推理模型会先"思考"再作答，
   思考部分同样计入这里。若开启思考，建议不低于 2048。
```

## 二、表单字段清单

### 2.1 连接信息

| 字段 | 类型 | 必填 | 默认 | 界面提示 |
|---|---|---|---|---|
| 配置别名 `name` | string(1-64) | ✅ | — | 「给这个配置起个名字，如：我的 DeepSeek」 |
| 协议类型 `provider_type` | 枚举 | ✅ | `openai_compatible` | 下拉框，选项来自 `GET /api/v1/system/provider-types` |
| API 地址 `base_url` | string | ✅ | — | 「需包含版本号，如 `https://api.deepseek.com`」 |
| API 密钥 `api_key` | string | ⭕ | `""` | 「本地部署（Ollama/vLLM）可留空」；输入框用密码类型 |
| 模型名 `model_name` | string | ✅ | — | 「如 `deepseek-flash`」；可提供「拉取可用模型」按钮 |

### 2.2 模型能力

| 字段 | 类型 | 范围 | 默认 | 界面提示 |
|---|---|---|---|---|
| 上下文窗口 `context_window` | int | 512 ~ 10,000,000 | 65536 | 「模型能记住的总长度（输入+输出），请按厂商文档填写。DeepSeek 128K、GPT-4o 128K」 |

### 2.3 生成参数（`generation` 对象）

| 字段 | 类型 | 范围 | 默认 | 界面控件 | 界面提示 |
|---|---|---|---|---|---|
| `temperature` | float | 0.0 ~ 2.0 | **0.8** | 滑杆 + 数字框 | 「越高越有创造性，越低越稳定。叙事建议 0.7~1.0」 |
| `top_p` | float \| null | 0.0 ~ 1.0 | `null` | 滑杆 | 「与温度二选一调整即可，同时调容易互相干扰。留空表示不发送」 |
| `max_tokens` | int | 1 ~ 131072 | **2048** | 数字框 | ★「最大输出 Token，**包含思考过程**」 |
| `reasoning_effort` | 枚举 | 见下表 | `auto` | 下拉框 | ★「思考强度。思考会占用输出配额」 |
| `frequency_penalty` | float \| null | -2.0 ~ 2.0 | `null` | 高级折叠区 | 「降低重复用词」 |
| `presence_penalty` | float \| null | -2.0 ~ 2.0 | `null` | 高级折叠区 | 「鼓励引入新话题」 |
| `stop` | string[] | — | `null` | 标签输入 | 「遇到这些词就停止生成」 |
| `seed` | int \| null | — | `null` | 高级折叠区 | 「固定随机种子可复现同一结果」 |
| `extra` | object | — | `{}` | JSON 编辑框 | 「厂商特有参数透传。以 `_` 开头的键不会发送到上游」 |

### 2.4 `reasoning_effort` 选项

| 值 | 界面文案 | 说明 |
|---|---|---|
| `auto` | 模型默认（推荐） | 不发送任何思考相关参数，最安全 |
| `off` | 尽量关闭思考 | 输出全部留给正文。**部分模型不支持真正关闭** |
| `low` | 轻度思考 | 响应快，思考约占输出的 30%~50% |
| `medium` | 中等思考 | 思考约占 50%~70% |
| `high` | 深度思考 | 思考可能占 80% 以上，正文空间被压缩 |

> ⚠️ `off` 在不同协议下能力不同：
> - OpenAI 兼容协议**没有真正的「关闭」**，最接近的是 `minimal`（最小思考）
> - Anthropic 支持 `thinking.type = "disabled"`，可以真正关闭
>
> 界面文案不要写「关闭思考」，应写「**尽量**关闭思考」。

## 三、上下文预算

后端会实时计算出预算拆解，前端应把它可视化出来，让用户直观看到「输出留太多、输入就没地方了」。

### 3.1 计算公式

```
输入预算 = 上下文窗口 − 最大输出 − 安全余量

安全余量 = max(128, 上下文窗口 × 5%)
```

### 3.2 接口返回的字段

`ProviderConfig.budget` 会返回：

```json
{
  "context_window": 65536,
  "max_output_tokens": 2048,
  "safety_margin": 3276,
  "input_budget": 60212,
  "output_share": 0.0312,
  "is_usable": true,
  "note": "max_output_tokens 包含思考过程 token（推理模型会占用大部分）"
}
```

### 3.3 推荐的可视化方式

一条按比例分段的横条：

```
┌────────────────────────────────────────────────────────────┐
│ 输入预算 60212 (92%)                │ 输出 2048 │ 余量 3276 │
└────────────────────────────────────────────────────────────┘
```

## 四、自动校验与提醒

后端把提醒分成**两类**，前端应分别用不同样式展示 —— 混在一起会让用户分不清「必须处理」和「可以了解一下」。

| 来源 | 含义 | 建议样式 |
|---|---|---|
| `warnings` | 当前配置**会影响效果**的问题 | 黄色警告条 |
| `hints` | **建议性**提示，不做也不影响正确性 | 灰色/蓝色信息条 |

### 4.1 `warnings`（黄色警告）

| 触发条件 | 提醒文案 |
|---|---|
| 已探测该模型忽略思考强度 **且** `reasoning_effort != auto` | 「实测该模型会忽略「思考强度」：设置为 high 后，思考量并没有明显变化。这个设置不会报错，但也不会有任何效果。建议改回 auto，改用「最大输出 Token」来控制正文长度。」 |
| 开启了思考 且 `max_tokens < 2048` | 「该模型开启了思考（high），而最大输出只有 512 token。思考过程可能占用大部分配额，建议调到 2048 以上，否则正文可能很短甚至为空。」 |
| `input_budget < 512` | 「输入预算仅剩 292 token，可能放不下角色设定与对话历史。」 |
| `output_share > 50%` | 「输出预留占了上下文窗口的 88%，留给提示词与历史的空间偏少。」 |
| 云端地址 且未填密钥 | 「未填写 API Key。云端服务通常都需要密钥，请确认。」 |

### 4.2 `hints`（灰色信息）

| 触发条件 | 提示文案 |
|---|---|
| `reasoning_effort != auto` 且**从未探测** | 「尚未验证该模型是否支持「思考强度」。部分模型会接受这个参数但完全不理会它（实测 DeepSeek 的 deepseek-flash 即是如此），建议先点「检测支持情况」确认（会调用模型 2 次）。」 |
| `reasoning_effort != auto` 且**探测结论已过期**（换过模型） | 「模型名已从「deepseek-flash」改为「deepseek-v4-pro」，之前的思考强度检测结论已失效，建议重新检测。」 |

> `reasoning_effort = auto` 时**永远不产生任何提示** —— 它不干预厂商默认行为，不存在「设了没用」的问题。

### 4.3 硬性校验（直接报错，不让保存）

- `max_tokens >= context_window` → 「最大输出 token 不能大于等于上下文窗口 —— 那样就没有空间放提示词和对话历史了」

## 五、★ 思考强度的「生效性检测」

这是本设计里最容易被忽略、但最影响体验的一环。

### 5.1 为什么需要它

**「有这个控件」和「这个控件真的有效」是两件事。**

实测数据（`deepseek-flash`，同一提示、`temperature=0`）：

| 思考强度 | 输出 token | 思考 token |
|---|---|---|
| `auto` | 218 | 153 |
| `high` | 235 | 172 |
| `low` | 183 | 133 |
| `off` | 254 | **175** |

模型**接受**了 `reasoning_effort`（不报错），但**完全忽略**它 —— 设成「尽量关闭」，思考反而更多。
这类「静默无操作」不报错、不给提示，只能靠对比实验发现。

### 5.2 检测方式

```
用同一提示、temperature=0，分别以 off 和 high 各调用一次，比较思考 token 数
```

判定阈值 **40%**（不是 15%）：

- 推理模型的思考长度本身就有 **±15% 的自然波动**（实测同条件连续 4 次：153 / 172 / 133 / 175）
- 真正支持关闭思考的模型，`off` 的思考 token 会**接近 0**，差异通常在 80% 以上
- 只有 10%~20% 的区别，那只是噪声，不能作为「参数生效」的证据

接口：

```powershell
POST /api/v1/system/probe-reasoning-effort
```

> ⚠️ 该接口**会真实调用模型 2 次**，界面上必须做成用户主动点击的按钮，不要在保存时自动触发。

### 5.3 检测结果要存下来

探测结论必须**持久化到模型配置上**（`llm_providers` 表的三列），否则用户点完就忘，下次进来还是不知道该不该信这个下拉框。

| 数据库字段 | 说明 |
|---|---|
| `reasoning_effort_supported` | `TRUE`/`FALSE`/`NULL`（NULL = 未探测） |
| `reasoning_effort_probed_model` | 探测时用的模型名 |
| `reasoning_effort_probed_at` | 探测时间 |

**★ 为什么必须记录「探测时用的模型名」？**

探测结论是**针对特定模型**的。用户把模型名从 `deepseek-flash` 换成 `deepseek-v4-pro` 后，
旧的「该模型忽略思考强度」结论就不再适用。有了这个字段，后端能自动判断结论是否过期：

```python
config.reasoning_probe_is_stale   # True 表示结论已失效，界面应提示重新检测
```

若不记录，界面会一直拿着过期结论误导用户 —— 跟不做检测一样糟。

### 5.4 接口返回结构

`GET /api/v1/providers/{id}`（3.6 实现）会返回：

```json
{
  "reasoning_effort_support": {
    "probed": true,
    "supported": false,
    "probed_model": "deepseek-flash",
    "probed_at": "2026-09-19T12:00:00",
    "stale": false
  },
  "warnings": ["实测该模型会忽略「思考强度」：……"],
  "hints": []
}
```

前端据此：`stale=true` 或 `probed=false` 时把「检测支持情况」按钮**高亮**，
提示用户点一下；`supported=false` 且用户选了非 auto 时展示黄色警告。

## 六、推荐的参数预设

给用户几个一键预设，比让他们自己摸索友好得多。

| 预设名 | temperature | max_tokens | reasoning_effort | 适用场景 |
|---|---|---|---|---|
| **创意叙事** | 1.0 | 4096 | `medium` | 剧情推进、场景描写 |
| **稳定续写** | 0.7 | 2048 | `low` | 需要保持人设与文风一致 |
| **快速对话** | 0.8 | 512 | `off` | 简单问答，追求响应速度 |
| **深度推演** | 0.9 | 8192 | `high` | 复杂剧情分支、逻辑推理 |

> 预设只是填充表单，用户仍可自行调整。若该模型已探测为「忽略思考强度」，
> 预设里的 `reasoning_effort` 会被降级为 `auto` 并给出提示。

## 七、前端实现提醒

1. **`max_tokens` 与 `temperature` 始终会发送**，其余为空的参数不发送 —— 这样行为可预期。
2. **`reasoning_effort = auto` 时不发送任何思考字段**。这是最安全的默认值：`reasoning_effort` 是较新的参数，不少模型和网关不认识它，贸然发送会直接换来 400。
3. 如果保存后测试连接报 400，且错误详情里有 `hint` 字段，说明该模型不支持 `reasoning_effort`，应提示用户改回 `auto`。
4. **`api_key` 永远不要回显明文**。`ProviderConfig.to_dict()` 已刻意不包含该字段；编辑时前端应显示占位符（如 `sk-****`），用户不修改则提交空值表示「保持原密钥」。
5. `warnings` 与 `hints` 必须**分开渲染**，否则用户无法分辨哪些是必须处理的。
