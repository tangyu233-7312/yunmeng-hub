## 2. ★ 核心章节：异构大模型适配层

### 2.1 两个协议的字段级差异（论文主表）

| 差异点 | OpenAI 兼容 | Anthropic Messages | 项目里的处理位置 |
|---|---|---|---|
| 端点 | `POST /chat/completions` | `POST /v1/messages` | `openai_compatible.py` / `anthropic.py` |
| 鉴权 | `Authorization: Bearer xxx` | `x-api-key: xxx` + `anthropic-version: 2023-06-01` | `anthropic.py` 的 `_headers()` |
| 系统提示词 | `messages` 里 `role=system` | **顶层独立参数** `system` | `anthropic.py` 的请求构造 |
| `max_tokens` | 可选 | **必填** | 两个适配器各自兜底 |
| 停止词 | `stop` | `stop_sequences` | `anthropic.py:257` 附近 |
| 消息交替 | 无要求 | **必须严格 user/assistant 交替且以 user 开头** | 连续 user 消息合并 |
| 回复正文 | `choices[0].message.content`（字符串） | `content[]` 数组，需按 `type` 过滤 | `anthropic.py:314-333`（`text` / `thinking` / `redacted_thinking`） |
| 结束原因 | `finish_reason` | `stop_reason`（**取值也不同**） | 各自归一化成 `finish_reason` |
| 流式格式 | `data: {"choices":[{"delta":…}]}` | **命名事件** `content_block_delta` | `anthropic.py:441-459` |
| 结束标记 | `data: [DONE]` | `message_stop` 事件 | 各自映射成统一的流结束 |
| 用量字段 | `prompt_tokens` / `completion_tokens` | `input_tokens` / `output_tokens` | 归一化成 `TokenUsage` |
| 思考强度 | `reasoning_effort: "high"` | `thinking: {budget_tokens: N}` | `anthropic.py:174-241` |
| 思考与采样 | 无约束 | **开启思考时禁止改 `temperature` / `top_p`** | 移除参数并写进 `notes` |

> 更完整的版本（含 14 行差异）见 `README.md` 的「两个协议的差异有多大」一节，以及 `app/llm/anthropic.py` 顶部的对照表注释。

### 2.2 一个统一枚举，三种协议表达

| 统一取值 | OpenAI 兼容 | Anthropic | 项目决策 |
|---|---|---|---|
| `auto` | **不发送任何字段** | 不发送任何字段 | 最安全：不假设厂商行为 |
| `off` | `reasoning_effort: "minimal"`（**并非真正关闭**） | `thinking: {"type": "disabled"}`（**可真正关闭**） | 如实标注差异 |
| `low` | `reasoning_effort: "low"` | `budget_tokens = max_tokens × 25%` | `anthropic.py:100` |
| `medium` | `reasoning_effort: "medium"` | `budget_tokens = max_tokens × 50%` | `anthropic.py:101` |
| `high` | `reasoning_effort: "high"` | `budget_tokens = max_tokens × 75%` | `anthropic.py:102` |

Anthropic 的两条硬约束（`anthropic.py:36-37`）：

```
1024 <= budget_tokens < max_tokens        （budget_tokens 还会被夹到这个区间内）
```

放不下时**直接报错并给出修改建议**，而不是偷偷关掉思考（`anthropic.py:44-46`、`app/llm/params.py` 模块文档）。
论文里可以把这条写成设计原则：**拒绝静默降级，宁可报错**。

### 2.3 错误码归一化（7 类）

| 统一异常 | 触发场景 | 是否重试 | 出处 |
|---|---|---|---|
| `LLMAuthError` | 401 / 403 | **否** | `app/llm/errors.py` |
| `LLMQuotaError` | 402 / 429 | 是 | 同上 |
| `LLMModelNotFoundError` | 404 | 否 | 同上 |
| `LLMTimeoutError` | 读取超时 | 是 | 同上 |
| `LLMConnectionError` | DNS / 连接失败 | 是 | 同上 |
| `LLMBadRequestError` | 400（参数错 / 上下文超长） | 否 | 同上 |
| `LLMUpstreamError` | 5xx | 是 | 同上 |

额外处理的一种坑：**部分厂商鉴权失败却返回 HTTP 200**，错误藏在响应体的 `code` / `error` 字段里 —— 适配层会识别并归类。

重试策略：指数退避 + 随机抖动；**只在「尚未输出任何内容」时重试流式请求**，避免前端看到重复错乱的文本。

### 2.4 适配层的改动必须回报（`notes` 机制）

| 触发条件 | 适配层实际做了什么 | 怎么回报 |
|---|---|---|
| Anthropic 开启思考 | 移除 `temperature` / `top_p` | `ChatResult.notes` / `StreamChunk.notes` |
| OpenAI 兼容要"关闭"思考 | 只能映射成 `minimal`（不是真关闭） | 同上 |
| Anthropic 消息不交替 | 合并连续 user 消息 | 同上 |
| Anthropic 思考预算换算 | `budget_tokens = max_tokens × 比例` | 同上，文案见 `anthropic.py:240-241` |

> 论文论点：**参数被适配层改过而不告知，等于静默误导**。这是本项目与"只把 base_url 做成配置项"的本质区别。

## 3. 上下文预算与裁剪

### 3.1 公式（全部可从代码复算）

出处：`app/llm/params.py:219-296`

```
安全余量   = max(128, context_window × 5%)
输入预算   = max(0, context_window − max_tokens − 安全余量)
可容纳历史 = 输入预算 − 系统提示词 − 滚动摘要 − 尾注 − 记忆预留(reserve_tokens)
```

其中 `max_tokens` 是**整块预留**，且它**包含思考过程 token** —— 这是全项目最容易搞错的一条规则
（`app/llm/params.py:1-27` 有完整说明，与 SillyTavern 行为一致）。

**可复算的示例**（用默认模型配置：窗口 65536、最大输出 2048）：

| 项 | 值 | 算式 |
|---|---|---|
| 安全余量 | 3276 | `max(128, 65536 × 0.05)` = 3276.8 → 取整 3276 |
| 输入预算 | 60212 | `65536 − 2048 − 3276` |

```powershell
# 一条命令复算，核对论文里的数字
.\.venv\Scripts\python.exe -c "from app.llm.params import compute_context_budget as f; b=f(65536,2048); print(b.safety_margin, b.input_budget, b.describe())"
```

> 注：`README.md` 里的 `58164` 用的是 `max_tokens=4096` 的示例（`65536−4096−3276=58164`）。
> **论文里写到具体数字时，务必先跑上面这条命令**，不要抄 README 的例子。

### 3.2 token 估算（不引入 tiktoken 的理由）

出处：`app/narrative/context_manager.py:18-74`

```
中日韩文字  1 字 ≈ 1 token
其它字符    1 字 ≈ 0.25 token（= 4 字符 1 token，向上取整）
每条消息    再加 4 token 结构开销（role / 分隔符）
```

**为什么不用 tiktoken**（论文可直接引用的工程判断）：

1. tiktoken 只服务 OpenAI 系；Claude 分词器不同，本地模型又各有各的 —— 装它反而给人"算得很准"的错觉；
2. 估算的目的是**决定丢哪些消息**，不是精确计费；
3. `ContextBudget` 里本来预留了 5% 安全余量来吸收估算误差。

> ★ **诚实标注**：该估算的「±10% 以内」是**工程经验值，本项目未做过对照实测**
> （没有跑过"估算值 vs 厂商返回的 `prompt_tokens`"的批量比对）。
> 论文里若引用，请写成"启发式估算 + 5% 安全余量"，不要写成"实测误差小于 10%"。
> 补实测的方法：`messages` 表里有 `token_count`，`llm_providers` 有真实调用 —— 可以对同一批提示词
> 比较估算值与厂商回传的 `prompt_tokens`，这是**可以补做的一个实验**。

### 3.3 裁剪顺序（从最不重要的开始丢）

出处：`app/narrative/context_manager.py:253-256`

| 顺序 | 丢弃对象 | 理由 |
|---|---|---|
| 1 | 最早的对话轮次 | 离当前剧情最远，压进「前情提要」 |
| 2 | 尾注 `post_history_instructions` | 宁可丢尾注也要保住剧情 |
| 3 | 系统提示词（按比例截断） | 最后手段，且**必须如实标注已截断** |

裁剪结果会带出 6 个数字给界面（`ContextPlan.to_dict()`）：
`estimated_input_tokens` / `input_budget` / `history_kept` / `history_dropped` / `summary_tokens` / `trimmed`。

### 3.4 滚动摘要为什么是本地压缩

出处：`app/narrative/context_manager.py:189-229`

| 方案 | 成本 | 延迟 | 本项目选择 |
|---|---|---|---|
| 再调一次模型生成摘要 | 每轮多一次调用 | 响应时间翻倍 | ✗ 否决 |
| 本地压缩（每条被丢消息留前 120 字） | 0 | 0 | ✓ 采用 |
| 掐中间留两头（上限 2000 字） | 0 | 0 | ✓ 采用，`SUMMARY_MAX_CHARS=2000` |

> 论文里的表述建议：**"压缩质量"与"每轮成本"之间做了显式的取舍**，
> 字段 `rolling_summary` / `summarized_until_message_id` 已按"将来换成模型摘要"预留，函数签名不变。

## 4. 两种记忆注入通道的对比（关键词触发 vs 向量召回）

| 维度 | 世界书关键词触发 | 向量长期记忆 |
|---|---|---|
| 实现 | `app/narrative/world_book_scanner.py` | `app/narrative/memory.py` + `app/db/chroma.py` |
| 匹配方式 | **字面子串包含**（不分词） | **语义近邻**（余弦距离） |
| 额外成本 | **0**（纯本地字符串匹配） | 每次写入/查询各一次嵌入推理 |
| 延迟 | 微秒级（只做一次 `in` 判断） | 取决于嵌入后端（本地 ONNX / 远程 API） |
| 擅长 | 人名、地名、专有名词 | "他答应过我的那件事"这类模糊指代 |
| 已知局限 | 「龙」会命中「龙虾」（子串误伤） | 相似度门槛定低了会召回错内容 |
| 触发窗口 | 最近 `scan_depth` 条（默认 8） | 当前会话全量（`top_k=5`，门槛 0.35） |
| 容量控制 | `token_budget`（默认 1024，**至少保留第一条**） | `MAX_BLOCK_CHARS=1200` + `reserve_tokens` 预算预留 |
| 幂等 | 无状态，天然幂等 | 记忆 ID = `mem-s{session}-{user_msg}-{assistant_msg}` |
| 故障处理 | 不涉及外部依赖 | **全部函数不抛异常**，只降级 + 回报 `memory_error` |

> 出处：`world_book_scanner.py:14-28`（4 条刻意决定）、`memory.py:12-29`（3 条设计决定）。
> **论文论点**：两者不是替代关系，而是**成本/语义两个维度的互补**，共同拼进同一个系统提示词。

### 4.1 记忆的一致性约束（可写成"删除一致性"小节）

| 操作 | 对话记录 | 长期记忆 |
|---|---|---|
| 删会话 | 级联删除 | **一并清掉**（`memory.forget_session`） |
| 清空记忆 | **不受影响** | 全部清掉（`memory.forget_all`） |
| 写入时机 | 先落库 | **对话成功落库之后**才写（否则会出现"记忆里有、对话里没有"的幽灵内容） |

验证：`tests/test_memory.py`（16 项）与 `scripts/smoke_test.py` 的「3.9」步骤（直连 ChromaDB 核对行数）。

### 4.2 ★ 混合检索：两路怎么融合（RRF）+ 装填优先级

前面两条通道不是各查各的：`app/narrative/retrieval.py` 把它们合成一条管道
（召回 → RRF 融合 → 跨通道去重 → 同分裁决 → **两级预算装填**）。

**消融实测**（离线合成标注集：12 query / 10 世界书条目 / 11 记忆；`scripts/benchmark.py`）：

| 策略 | Recall@1 | Recall@3 | MRR | nDCG@5 | 注入条数(均) | 注入 token(均) |
|---|---|---|---|---|---|---|
| 只用关键词通道 | 0.4861 | 0.5278 | 0.7917 | 0.5768 | 1.17 | 34.7 |
| 只用语义通道 | 0.2917 | 0.3889 | 0.7083 | 0.4493 | 2.00 | 42.7 |
| **RRF 融合（默认）** | **0.5139** | **0.9167** | **0.9167** | **0.8962** | 3.08 | 74.5 |
| 融合 + 字面重叠重排（负面对照） | 0.3056 | 0.8750 | 0.8194 | 0.7765 | 3.08 | 74.5 |

复现：`.\.venv\Scripts\python.exe scripts\benchmark.py` → `data/benchmark_report.{json,md}`

两条**被数据推翻的直觉**（都写进了代码注释与回归测试，是很好的"实现难点"素材）：

1. 用"与查询的字面重叠"去重排**有害**（Recall@1 0.51 → 0.31）：语义通道的价值
   恰恰在于命中**没有字面重叠**的同义改写。
2. RRF 是**名次**融合，同分极其常见 —— "怎么裁决同分"对 Recall@1 的影响和融合策略本身一样大：
   按 key 字母序 0.5139 / 按先验分 0.2639 / 只按语义分 0.3333 / **按每路归一化证据 0.5139**。

**装填优先级（用户拍板的硬规则）**：**世界书 ≥ 预设 > 用户对话 / 回忆**。
`pack()` 两级装填：先按分数装世界书条目，再用**剩余预算**装回忆 ——
回忆再高分也**不能挤掉**作者手写的设定（丢一条设定就可能让角色出戏、掉马甲）。
守卫测试：`tests/test_retrieval.py::test_world_book_entries_are_never_evicted_by_memories`。

### 5.1 推理模型把输出配额花在思考上

| 指标 | 值 | 出处 |
|---|---|---|
| `completion_tokens` | 433 | `app/llm/params.py:14-17` 记录的实测（`deepseek-flash`，一次叙事场景描述） |
| 其中 `reasoning_tokens` | 380 | 同上 |
| 思考占比 | **88%** | `380 / 433` |

**工程后果**：`max_tokens` 给小了会出现 `finish_reason=length` + HTTP 200 + **正文为空**的"静默空回复"。
本项目已加 `_raise_if_no_content` 守卫并给出可操作报错。

### 5.2 思考强度参数「被接受但被忽略」

同一提示、`temperature=0`，分别以「尽量关闭思考」与「深度思考」各调用一次，比较思考 token 数（`deepseek-flash`）：

| 轮次 | off | high | 差异 |
|---|---|---|---|
| 第 1 次 | 124 | 134 | **+7%** |
| 第 2 次 | 117 | 170 | **+31%** |
| 第 3 次 | 135 | 75 | **−44%**（high 反而更少） |

结论：`deepseek-flash` **接受但不理会** `reasoning_effort`，思考量始终在 100~170 之间随机波动。
参考基线（同条件连续 4 次）：`153 / 172 / 133 / 175` —— 自然波动就有 ±15%。

因此判定阈值定为 **40%**，而不是 15%（出处：`README.md` 的「思考强度并非所有模型都支持」一节，
实现见 `app/llm/diagnostics.py`）。

> 论文价值：这是"参数不报错 ≠ 参数生效"的典型案例，比返回 400 更危险。

### 5.5 ★ 状态漂移曲线（"状态一致性校验"值不值的量化证据）

**问题**：模型每轮自称的 `<state>` 会写飘（HP 越滚越高、脏值混进背包）。
`app/narrative/state.py` 的校验（越界夹取 / 上限跳变护栏 / 脏值丢弃 / 未知字段忽略）
到底值不值？只报"修正了 3 处"说明不了问题，要给**随轮次变化的曲线**。

**做法**（`app/narrative/state_drift.py` + `scripts/benchmark_data/drift_script.json`）：

### 5.6 ★ 骰子插件：让"随机"真的不可被叙述者决定（可写进"插件化架构"一节）

**问题**：跑团 / 检定 / 掉落表的乐趣建立在"结果不由叙述者决定"上，
但大模型**没有真随机**：同一个提示词下它倾向于给出"恰到好处"的数字
（需要成功就写 18、需要失败就写 3），同一个骰点两次回答还能不一样。
如果让模型"自己掷"，等于让叙述者同时当裁判。

**做法**（`app/narrative/dice.py` + 插件类型 `dice`）：

- **受控求值器**：自己写的递归下降解析器（分词 → 四则 → 一次比较），
  **不用 `eval`、不放开 JS**（与"插件绝不执行第三方 JS"同一条红线）。
  支持 `NdM`、`kh`/`kl` 取高取低、`!` 爆炸骰（有深度上限）、括号、
  `<= >= < > = !=` 成功判定。上限全部显式（长度/骰子数/面数/括号深度/爆炸次数/结果绝对值），
  超限**拒绝并说明原因**，不"截断后照算"。
- **两条入口同一个求值器**：玩家 `/r 1d20+5 力量检定`；模型 `<roll>1d20+5</roll>`
  （后端把标签替换成明文点数，下一轮模型在历史里看到的就是真实数字）。
- **点数落库、绝不重掷**：在"用户消息唯一落库点"掷定并写进 `messages.rolls_json`
  （含逐颗骰面与取舍过程）。这样刷新页面、「查看提示词」预览、重新生成读到的都是
  **同一组数字** —— 若改成构建提示词时现掷，点一次预览就会掷出另一个数
  （本文的"预览与实际必须一致"原则在此又一次起作用）。
- 提示词分两处：**规则**（"你没有随机数能力 + 怎么写 `<roll>`"）加在系统提示词**末尾**
  （机械指令越靠后越有效）；**本轮点数**是客观事实，放在「当前状态」之后、守卫之前。

**可复现体检**（`scripts/benchmark.py` 的 `[8]` 节，固定种子 20260926）：

| 记号 | 含义 | 实测均值 | 理论均值 | 实测范围 | 合法范围 |
|---|---|---|---|---|---|
| `1d100` | 百分骰 | 50.91 | 50.50 | 1~100 | 1~100 |
| `d20` | 省略个数 = 1 | 10.59 | 10.50 | 1~20 | 1~20 |
| `2d6+3` | 加常数 | 10.03 | 10.00 | 5~15 | 5~15 |
| `4d6kh3` | 四取三（属性生成） | 12.23 | — | 3~18 | 3~18 |
| `4d6kl1` | 四取低一 | 1.77 | — | 1~6 | 1~6 |
| `2d6!` | 爆炸骰（有深度上限） | 8.47 | — | 2~43 | 2~132 |
| `(1d6+2)*2` | 括号与乘法 | 11.07 | 11.00 | 6~16 | 6~16 |
| `1d20+5<=15` | 成功判定 | 15.59 | — | 6~25 | 6~25 |

> 1d6 分布卡方 = 5.00（df=5；p=0.05 临界 11.07，p=0.001 临界 20.52）→ 看不出偏斜；
> 同种子两次逐位一致，不给种子时结果不重复；**8 种记法 48000 次掷骰零越界**
> （求值器输出按构造不可能越界 —— 与 §5.5"反事实脏值率 52.5%"形成对照：
> 让模型自己编数字，脏值一旦写进去就洗不掉）。
> 复现：`.\.venv\Scripts\python.exe scripts\benchmark.py` → 控制台 `[8]` 节 ·
> `data/benchmark_report.json` 的 `dice` · `data/benchmark_report.md` 的骰子表。

> ★ 论文里"这不是证明随机性"要写清楚：伪随机数无法被证明，这套体检的作用是
> **排掉低级错误**（面数写错、漏掉爆炸上限、取高取低写反），并给出可复现证据。

### 5.7 ★ 角色卡 VN 模式：把"表现层"也做成声明式（可写进"角色卡扩展"一节）

**问题**：角色卡作者想做"视觉小说"式的表现（背景 + 立绘 + 对话框），
但本项目既不引入图片生成，也不允许插件执行代码。要让立绘**跟着剧情变**，
直觉做法是加一个新标签（如 `<expr>生气</expr>`）—— 那等于再发明一套协议。

**做法**（`app/narrative/vn.py` + 卡 `extensions.hne.vn`）：
**表情就是状态栏里的一个字段**（默认 `mood`），不新增任何协议。

```
卡:  "sprites": {"平静": "…/calm.png", "生气": "…/angry.png"}, "expression_field": "mood"
模型这一轮: <state>{"mood": "生气"}</state>
后端:      detail.vn.sprite_url = "…/angry.png"（按当前状态算）
前端:      背景 + 立绘 + 名牌（显示「生气」）+ 最后一句台词
```

三条设计理由（论文里可当作"扩展点如何与既有协议正交"的例子）：

1. **零新增协议**：模型从第六轮起就每轮输出 `<state>`，多一个字段**不增加一次调用**；
2. **同步性**：立绘与文字剧情来自同一个状态对象，不会"嘴上说生气、脸上还在笑"；
3. **字段由作者定义**：作者没写该字段时，建会话会自动补一个，并把**可选表情写进字段描述**
   —— 模型因此知道该填哪些词，而不是瞎写一个没有立绘的词；
   作者自己定义过则一个字都不改（尊重卡的作者，与第六轮同一取舍）。

**工程上的取舍**（可写成"安全边界"）：

| 项 | 做法 | 理由 |
|---|---|---|
| 图片地址 | 只收 `http(s)` 与 `data:image/(png/jpeg/webp/gif);base64` | `javascript:` / `file:` 不能进 `<img src>` |
| SVG | **明确拒绝** | SVG 可带脚本；`<img>` 里多数浏览器不执行，但"能不能执行"不该取决于浏览器版本 |
| 体积 | 单条 ≤300KB 字符、≤24 张 | 配置住在卡的 `extra_data`（MySQL JSON）里 |
| 坏数据 | 丢那一条 + 记 warning，**不废整张卡** | 与"一条世界书写坏不该让整张卡不能用"同一取舍 |
| 写入时机 | 卡 create/update/import 三条写入口统一归一化 | 存进去的就该是干净的，不能等渲染时才过滤 |
| 背景渲染 | 用 `<img>` 而不是 CSS `background-image` | 地址来自用户，拼进 `style` 属性要担心 CSS 字符串逃逸 |

> 顺带一个可复用的结论：**"前端只画、后端算"** 让这条规则可以被自动化断言
> —— pytest 直接断言 `detail.vn.sprite_url`，浏览器探针断言 DOM 里的 `src`，
> 两边都不会各写一套映射。本轮在这条链路上抓到并修掉了探针里的一个
> "旧 view signal"竞态（见 `docs/pitfalls.md` 第 35 条与 §27.4）。

**复现**：`.\.venv\Scripts\python.exe -m pytest tests/test_vn.py -q`（21 条）；
浏览器侧：`scripts\ui_probe.py` 的 `14.VN立绘` 节（5 条）；
**可直接放进论文的图**：`docs/vn-screenshot.png`（探针在真实界面里截的：
状态栏 `mood` 改成「生气」后立绘与名牌都跟着变；图是探针内嵌的纯色小图）。

> ★ **证据边界（论文里要如实写）**：探针用的是**内嵌纯色小图**（探针必须离线可跑），
> 它断言的是"地址取自卡、表情→立绘由后端算"这条**逻辑**；**排版观感**自动化证明不了 ——
> 透明底 PNG 的合成、真实长宽比下的取景、背景 `object-fit: cover` 的裁切、
> `sprite_scale` 放大后被 `overflow: hidden` 裁顶，这些只能人工复核一次。
> 复核办法：在卡编辑器 🎭 VN 立绘里填**真实立绘地址**（`http(s)://` 或
> `data:image/...;base64,`，单条 ≤300,000 字符、最多 24 张）后开舞台逐项看。

### 5.8 ★ 自动翻译中间件：把"语言"当成一个可替换的中间层
**问题**：大量角色卡是英文/日文写的。中文用户直接聊会有两个后果：模型被"卡的语言"
带着走（回你一串外语），以及用户自己写的句子模型可能理解偏。集成翻译 API 会引入
外部依赖与额外密钥，与本项目"复用统一 LLM 调用层"的架构也不一致。

**做法**（`app/narrative/translate.py`）：复用**统一 LLM 调用层**里的任意模型配置
（含"单独指定一个更便宜的模型专门翻译"）做这一步，于是"用哪个模型翻译"
本身也成了可对比的实验变量。

**三档模式体现了"成本必须由用户选"这条项目原则**：

| 模式 | 额外调用 | 论文里可以怎么写 |
|---|---|---|
| `off`（默认） | 0 | "未经用户同意不花 token"（与记忆总结同一条规矩） |
| `prompt` | **0** | 只用一句提示词约束输出语言：0 成本，但不保证（模型可能不听话） |
| `middleware` | 每轮 1 次 | 生成后真的调一次模型翻译：可靠，但每轮多一次调用 |

**两条省钱的本地判断**（不调模型，可写成"工程优化"）：
- **已经是目标语言就不译**：中文看 CJK 占比 ≥40%、英文看 ASCII 字母占比 ≥70%
  （判得保守：宁可多译一次，也不漏译）；
- **超过 6000 字不译**：一轮几千字的翻译很贵，且多半是整段剧情复述。

**一条必须写清楚的不变量**（否则界面与提示词装配会互相打架）：

```
messages.content                = 模型看到的文本（输入侧=译文，输出侧=模型原文）
messages.translation_json.text  = 给人看的文本（输出侧=译文，输入侧=用户原话）
```

把输入侧的译文写进 `content` 是有意为之：提示词装配**只读 `content`**，
于是不需要任何"替换历史"的机制 —— 少一处改动就少一处"预览与实际不一致"的机会。
界面则按"另一份"渲染，两份文本都在 DOM 里，切换是纯前端的（不发请求、不改数据）。

**跨链路的一个隐蔽 bug（值得写进"实现难点"）**：长期记忆如果按 `content` 写入，
跨语言会话里存进去的就是外语原文，而用户是用中文提问、检索也是中文 ——
下一轮召回质量会明显下降（表现为"模型突然记不住约定了"）。
解法是写记忆时统一取**给人看的那一份**（`engine._display_message`）。

**成本与降级**：翻译消耗计进 `session.total_tokens`，并在这一轮的提醒里如实写出来
（"本轮回复已由翻译中间件译成简体中文（47 token）"）；失败只记提醒与日志，
回复一个字都不会丢（与剧情总结降级同一套哲学）。

**★ "成本可见"这件事本身要单独验证（第十六轮真机对账）**：只读查库发现用户那轮
**1618 字符的英文回复（生成用量 700 token）翻译一次花了 5291 token** —— 因为该模型
**自带思考**（回复里也有"思考 323"），而翻译调用继承了会话模型的参数，`estimate_cost`
只按原文字数粗估、**不含思考 token**，面板的"这一轮预估"于是严重偏低。
两条处理：① 翻译请求改为请求 `minimal` 思考（**仅当该模型被探测为支持**时才发这个参数 ——
很多网关不认识它会直接 400，翻译失败等于用户白等一场，不值得冒险）；
② 面板标注"粗估，不含思考 token"。
★ **这条改动第一版是"静默失效"的**（第十六轮续修好）：探测结论挂在 `ProviderConfig` 上，
而适配器只带走 `GenerationParams`，调用侧问不到它；那个 `try/except` 把 `AttributeError`
吞掉、函数永远返回"不覆盖"，而单测伪造了一个**真实代码里不存在**的 API
（`default_params.effective_reasoning_support()`）所以照样绿。
修法：让结论跟着适配器走（`adapter.reasoning_support`，failover/whole_reply 透传），
并且**去掉那个 try/except**（接口变了就该炸出来），另加一条"结论必须到达适配器"的守门测试。
**可复用的结论**：`except Exception` 包住属性访问 = 把"接口用错了"变成一个无声的 no-op；
测试替身必须只伪造**真实存在**的接口，否则它守的是幻觉（本项目红线里"拒绝静默降级"的另一面）。
**可复用的结论**：凡是"给用户看的成本数字"，都必须拿**真机账单**回代核对一次 ——
纯函数单测只能证明公式算得对，证明不了公式**算的是不是同一件事**。
★ 第十六轮起每轮真实用量（厂商 prompt/completion/reasoning + 我们的输入估算）落在
`messages.usage_json`，`scripts/token_accuracy.py` 只读回放即可出"估算 vs 实测"对照表。

**复现**：`pytest tests/test_translate.py -q`（23 条：三档模式 / 两个方向 /
语言短路与源语言识别 / 太长跳过 / 失败不抛 / 独立翻译模型 / 两份文本落库 / PATCH 语义）；
界面侧：`scripts\ui_probe.py` 的 `15.翻译` 节（8 条）；
**可直接放进论文的图**：`docs/translate-screenshot.png`
（头部「🌐 翻译开」+ 气泡里的中文译文 + 「简体中文译文 · 47 token ｜ 看看另一份」）。

**★ 第十六轮的设计收敛：一个目标语言 + 源语言自动识别**（可写进"设计决策"一节）

初版把语言做成两个设置：输出侧「译成什么」+ 输入侧「译成什么」（默认英文）。
真实用户试用后给的反馈是**"默认居然是中文翻译成英文，我还得自己切换语言"** ——
根因不是默认值，而是**两个语言框并排时的语义歧义**：用户把"译文语言（输出侧）= 英文 /
译成哪种语言（输入侧）= 简体中文"读成了"英文 → 中文"，而代码语义恰好相反
（是"把回复译成英文"与"把我的输入译成简体中文"），于是配好之后**什么都不发生**。

收敛后的模型（`translate.py`）：

| | 初版 | 现在 |
|---|---|---|
| 语言设置 | 输出侧 + 输入侧两个 | **只有一个「翻译成什么语言」**，默认 `简体中文` |
| 源语言 | 隐式（输入侧靠 `input_lang` 反向指定） | **本地自动识别**（假名/谚文/简繁/字母占比） |
| 面向中文用户 | 需要用户自己想清楚两个框 | 开箱即用：外语回复 → 中文；自己写中文时 0 token 直发 |

> 论文口径：把"语言"从**用户要配置的两个参数**降级成**系统自动识别的内部状态**，
> 用户只需要表达意图（"我要看中文"）。这条和"成本必须由用户选、其余判断交给系统"
> 是同一套产品判断 —— **需要用户花钱的选择权交给他，不需要他操心的推断留给系统**。

**★ 顺带修掉的一个真 bug（很好的"实现难点"素材）**：源语言自动识别一度是**假的** ——
"已经是目标语言就不译"的判据是 **CJK 占比 ≥ 40%**，而 CJK 字符集里混进了
**平假名/片假名与谚文**。后果：模型用**日文**或**韩文**回复时被判成"已经是简体中文"
→ `used_model=false`、0 token、**静默不译**，用户看到的是没翻译的原文，
而界面上一切正常（"日文自动识别后翻成中文"配好了却什么都不发生）。
修法：汉字区与假名/谚文分开判，再对中文做**简繁专用字**判定（含繁体专用字要转简、
含简体专用字要转繁），判不出来就老实译。这类 bug 的教训是：
**"本地短路"必须和它要近似的那个集合严格同名，否则省下的是钱、丢掉的是功能。**

**真模型上的效果与花费怎么验（自动化探针证明不了的部分）**：探针与冒烟一律用假模型
（`FakeAdapter` / `scripts/fake_openai_server.py`），它们只能证明**链路**是对的，
**译文质量与真实 token 花费必须用真模型跑一轮**。方法：
1. **不需要外语卡**：译成哪种语言是**面板设置**、不是卡属性，且源语言自动识别。
   拿任意中文卡把目标设成英文（或直接用一张外语卡、目标留成默认的简体中文）即可跑通；
   注意你写中文、目标也是中文时会命中"已经是目标语言"→ 0 token（设计如此）。
2. **花费怎么看**：🌐 面板的「这一轮预估 / 翻译累计」、每轮提醒里的 `(N token)`、
   以及 `session.total_tokens`（翻译消耗计进会话累计）；逐条留痕在
   `data/logs/app_*.log` 的 `回复已翻译 | … tokens=…` 一行。
3. **质量看四点**：标签保真（`<state>` 必须原样保留，否则状态栏会瞎）、只输出译文
   （无"译文："前缀、无引号）、专名跨轮一致、`content` / `translation.text` 两份文本的不变量。
4. 测试卡：`data/test-cards/translate-test-emily.json`（英文角色 + `state_schema: mood/affection`，
   模型每轮会带 `<state>`，正好用来验标签保真）。
   ★ **v1.0 → v1.1 → v1.2 的三次迭代（真机反馈驱动的，很适合写"实现难点"）**：
   v1.0 把 "always reply in English" 写在**自定义 `system_prompt`** 里 —— 而本项目（为兼容酒馆）
   让卡自带 `system_prompt` **整体替换**引擎自动拼装的那一份（`prompt_builder.py:261-289`），
   于是内置扮演规则与人设字段全被一句英文挤掉，模型**跟着用户的语言走**（"一会中文一会英文"）。
   v1.1 把语言要求挪到**尾注 `post_history_instructions`**（发出的最后一条消息）—— 真机结果
   **仍然全中文**：本文实测证明了尾注确实送达（`build_messages` 追加为最后一条、
   `context_manager.py:299-304` 裁剪层专门保住它、适配器 1:1 全发、用户插件为空壳），
   所以结论是**模型没照做** —— 因为此时 system 角色里是引擎用**中文**拼装的人设框架。
   v1.2 把语言规则写回 **system 角色**（卡的自定义 `system_prompt`，并且写成英文的完整提示词，
   自带人设与文风），尾注仅作强化。
   **可复用的结论**：①"位置最高"≠"模型一定照做"，持续性约束属于 system 角色；
   ②"替换 vs 追加"这类语义差异必须写进界面文案，否则用户（和开发者）都会踩；
   ③ 跨语言场景下**提示词本身的语言**是隐性变量 —— 引擎自动拼装的人设是中文的，
   它会把"角色说外语"这件事往回拉（对照卡 `translate-test-emily-pure-en.json` 用来二分定位
   中文状态契约的影响：主卡系统提示词 1239 字含 133 个中文字，纯英对照卡 964 字含 0 个）。

### 5.9 ★ 界面视觉：把"换肤"做成声明式插件（论文"界面设计"一节的素材）

**问题**：控制台最初是"白底后台管理风格"，与"沉浸式叙事"的气质不符；但如果直接把默认样式
改成深色，又会牺牲可读性与可维护性（散落各处的写死颜色无法被任何主题覆盖）。

**做法（分两步，第二步才是设计）**：

1. **先把颜色语义化**：组件里所有写死的 `#fff` / `#fafbfc` / 浅色边框收进
   `--surface` / `--surface-2` / `--surface-3` / `--*-border` / `--catalog-accent` 等变量。
   浅色默认值一字未改；这一步让"换肤"从"改几十处规则"变成"改一组变量"。
2. **主题是一条声明式插件**（`kind: css`）：内置目录里给出「云梦枢 · 星云暗涌」，
   内容是"变量赋值 + 补几处变量表达不了的规则"（星云径向渐变、`backdrop-filter` 毛玻璃、
   顶栏 1px 光带、滚动条）。用户一键启用/停用，**完全可逆、不动任何数据**。

**设计原则（来自"沉浸但不打扰阅读"）**：

| 原则 | 落地 |
|---|---|
| 装饰只在**外围** | 星云背景固定在页面底层（左上紫 / 右下青，各 8%），正文区对比度不受影响 |
| 不用纯白文字 | `--text:#e8eaf2`，久看不累 |
| 颜色有**分工** | **量子紫 `#A78BFA` = 状态**（选中、"我"的声音）、**极光青 `#00E5FF` = 交互**（悬停、聚焦、AI 侧微光）—— 而不是"到处都用同一个亮蓝" |
| 不做大面积色块 | 品牌色只出现在细线、描边、微光上（大面积色块会抢走对文字的注意力） |
| 不动效 | 刻意不加过渡与脉冲，避免"晃眼" |

**工程上的两点自证（可直接写进论文的"质量保障"）**：

* **变量完整性测试**：从 `styles.css` 的 `:root` 抓出所有"值是颜色"的变量，
  要求深色主题全部定义 —— 少一个，那个组件就会退回浅色默认值。
  这条测试**当场抓到过 4 个漏项**（也抓到过我判据写宽导致的误报）。
* **浏览器探针**：断言"星空渐变/毛玻璃/新图标**真的生效**"（读 `getComputedStyle`
  与 `img.naturalWidth`，而不是检查 CSS 文本里有没有那行字），
  并采样整页**实际绘制出来的颜色**，要求深色主题下不出现浅色块。
* **"覆盖有没有赢"要靠量、不靠看**：改完配色后我盯着截图怀疑"选中态仍是实心色块"，
  于是加了一条断言直接读计算样式（`rgba(167,139,250,.2)` / `inset 3px` / `50%`…）——
  **结论是覆盖一直正确，眼睛错了**。这条断言同时守住"哪天选择器优先级变了，
  选中态悄悄退回大色块"。
  （小坑：计算样式会把 `#a78bfa` 归一化成 `rgb(167, 139, 250)`，判据写十六进制会假红。）

**采样器自身的三次修正**（可作为"如何验证视觉"的方法论）：

| 版本 | 盲点 | 修法 |
|---|---|---|
| v1 | 只比 `backgroundColor` | —— |
| v2 | ①透明背景（白来自父级/子文档）②**渐变**画在 `background-image` 上 | 透明项单独报告 + 解析渐变色标 |
| v3 | ③**半透明**（`rgba(255,255,255,.05)` 被当成亮色） | **先按 alpha 合成到底色再算亮度** |
| v4 | ④**点状高光**（1.4px 的星点被当成"一整块 80% 白"） | 按**层**切分渐变（括号配对，不能按逗号）+ 声明尺寸 ≤4px 判为点状高光：单独报告、单独断言 |

**视觉参数也要用数字定，不能靠"看着差不多"**：星点做了四版才让用户看见 ——
v1 峰值 31（"看不出有什么不一样"）→ v2 56 → v3 116（"好像没区别，还是一片黑"）→
v4 **160、亮点占比 0.161%（3.2 倍密度）**，仍暗于正文（230）。
**结论：观感上的"有/没有"由密度主导，不是亮度** —— 把 v3 截图放大 3 倍才看清
"145×260 的区域里只有 4~5 个灰点"：参数上"有星星"，观感上就是"一片黑"。
**测量条件也要与用户一致**（探针改用 1920×1020 留档与采样）。

**另一条可写进论文的工程点：内置配置的"升级"问题**。
声明式插件的内容在**用户点「添加」时被拷贝**进数据库，于是内置条目（尤其主题）升级后，
用户看到的仍是旧版 —— 而且**没有任何地方会告诉他**。做法：
目录接口给出 `update_available`（已添加且内容与当前目录不同），界面显示「有更新」+「更新到最新」，
同一个接口按情况返回 201（新建）/ 200（覆盖更新）/ 400（已是最新，不假装成功）。
> 对论文的意义：**"声明式 + 拷贝式安装"必须配一条升级通道**，否则"我修好了"和
> "用户看到修好了"之间会永远差一步 —— 这次差了三轮。

> 结论：**"没测到"和"通过"长得一模一样**。视觉断言必须对着"人眼看到的结果"写，
> 而不是对着"最容易取到的字段"写；每换一种画法（背景/渐变/边框/子文档/半透明）
> 就要补一条对应的断言。

## 6. 踩坑记录：问题 → 根因 → 修复（论文"实现难点"一节）

> 完整版见 `docs/pitfalls.md`。这里挑 12 条**最能体现工程判断力**的

| # | 现象 | 根因 | 修复 | 为什么难发现 |
|---|---|---|---|---|
| 1 | Web 服务一切正常，但独立脚本**静默挂死** | 非重入锁在同一线程二次 `acquire()` = 永久阻塞（`db/mysql.py`、`embeddings/api_backend.py` 各一次） | 持有锁时绝不调用会加同一把锁的函数 | 没有任何报错、CPU 占用为 0，看起来像"在跑" |

|---|---|---|---|---|
| 11 | 在**插件页**点「删除」弹出**两个**窗，第二个还报 404「提示词预设不存在」 | 第 10 条只修了"同一视图重复绑定"。而 `presets.js::nextController` 换新控制器时**没接视图信号** —— 切页时 `routeAbort.abort()` 摘不掉它；又因为预设页与插件页的卡片同为 `.cc`、删除按钮同为 `data-act="del"`，插件页的点击被预设页留下的动作接走，拿**插件的 id** 去删预设 | ①控制器接力视图信号；②五个列表各带 `data-view` 归属校验（与信号无关的第二道防线）；③探针新增**走用户那条路**（先预设页再插件页）的断言：恰好 1 个窗且标题是「删除插件」 | ★ **老断言一直是绿的**：它只在本页反复点击，而这条 bug 必须"先访问 A 页再切到 B 页"才出现。另外旧的静态测试只数 `{ signal }` 的个数，而这里是经 `withSignal()` 间接绑定、变量名也换了 —— **数字对得上，bug 照样在** |
| 12 | 深色主题下，角色卡页永远有一整块白，换什么主题都换不掉 | ①HTML 开场白渲染在 `srcdoc` iframe 里 —— iframe 是**独立文档，父页面的 CSS 变量一个都进不去**，而那段文档头写死了 `background:#fff`；②**真正让用户看到的那块白是开场白预览框 `.cc-greeting` 的写死浅色渐变**（`linear-gradient(180deg,#f7f9fc,#f2f5fa)`） | ①iframe 文档头改成渲染时从父页面读当前主题变量注入（`ui.js::richDocHead()`）；②`.cc-greeting` 改用 `var(--surface-3)/var(--surface-2)` + `var(--text-dim)`；③探针单独**把 iframe 拆开量**（深色下实测 `rgb(22,28,38)`）并升级为**渐变感知**采样 | ★ **我在这里判断错了一次**：查到 iframe 写死 `#fff` 就宣布"定案"，用户复测后说"还是在"。第二个原因是**渐变画在 `background-image` 上**，`backgroundColor` 读出来是透明的，老采样把它当透明块**跳过**，而且它**不在采样清单里** —— "没测到"被报告成了"通过"（最危险的假绿） |

> 第 11、12 条的论文价值：**"修过了"不等于"修对了"**。
> 一个防御机制（abort signal）只要在**一处忘了接力**就整体失效，
> 而失效的表现是"在另一个页面上" —— 所以自动化断言必须复现**用户的真实路径**
> （先过 A 页、再切 B 页），而不是就近再点一次。
> 同样地，**视觉断言必须覆盖"真正被画出来的东西"**：渐变（`background-image`）、
> iframe/子文档、伪元素都不在 `backgroundColor` 里 —— 对它们单独取样，
> 否则"没测到"会被报告成"通过"。
> 最后一条更值钱：**先让用户确认位置，再宣布定案** —— 我这次把
> "我找到一个真 bug"当成了"我找到你说的那个 bug"，白绕了一轮。

## 7. 可写入论文的"设计原则"清单

这些是本项目**反复自我约束**后形成的规则，每一条都有对应的真实事故：

1. **拒绝静默降级，宁可报错** —— 用户明确要求了思考却放不下预算时，报错而不是偷偷关掉。
2. **适配层改动用户参数必须回报** —— `ChatResult.notes` / `StreamChunk.notes`。
3. **能被用户看见的状态必须如实回报** —— 裁剪了几条、命中了几条、被预算丢掉几条、记忆检索失败原因。
4. **预览必须与真实请求同源** —— `engine.build_session_prompt()` 一个函数两处调用。
5. **破坏性操作要显式确认** —— 删角色卡默认拒绝，必须带 `force=true`。
6. **越权规则按资源语义分别设计** —— 模型配置一律 404（避免泄露存在性），公开角色卡 403（调用方刚读过它，404 反而像"被删了"）。
7. **用户消息先落库、再调模型** —— 模型失败不该把用户打的字一起吞掉。
8. **记忆坏了只降级，不能拖垮主流程** —— `memory.py` 所有函数不抛异常。
9. **成本敏感** —— 每轮对话不多花一次模型调用（滚动摘要用本地压缩）。
10. **测试全绿 ≠ 没问题** —— CSS/JS 的 bug 只能靠真实浏览器发现，所以项目自建了 CDP 探针。
